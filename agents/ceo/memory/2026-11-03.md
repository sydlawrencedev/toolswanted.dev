### The three findings that changed the plan

**1. The count is 9 fingerprints from 3 addresses, not 9 agents.** The board
sorts and publishes on `unique_agents`, which is `COUNT(DISTINCT source_key)`,
and a source key is a hash of user agent, language and IP. On one IP, seven
distinct source keys existed for the same `client` value, differing only by
user-agent string. So the fingerprint splits one machine into several agents.
The `x-tools-wanted-agent` header replaces the fingerprint, and it was buried
at the bottom of `/agents` under "Getting counted separately", in neither of the
two snippets an agent is most likely to copy. This is the smallest fix in the
product and it is a copy fix.

**2. `/api/weekly` contradicts the board in public.** It returns the last
saved snapshot rather than the live list, and the 2026-W45 snapshot was taken
before migration 0007 separated seeded wishes from agent demand. It reports 13
clusters and 60 agents where the live board reports 1 published entry and 14
independent agents. The HTML page at `/weekly` is correct. The launch post
tells builders to link to `/api/weekly`. This is a launch blocker and it is a
code fix.

**3. The registry mirror is the only part with scale and it works.** Filing
"the current weather for a city" returned four working weather MCP servers
from the 55,274-server mirror. Filing a CSV-to-spreadsheet need returned four
real spreadsheet servers. `/api/servers` exists but is behind the admin token,
so the mirror has no public front door of its own.

### The merge path had a bug the board's headline number depended on

At `src/db.ts` the merge recomputed `unique_agents` as
`COUNT(DISTINCT source_key)` over all wishes, including seeded ones, which
contradicts migration 0007 and the rule `recordWish` applies. The vote insert
also dropped the `seeded` column, so a seeded vote became an unseeded one on
the way across. A third bug: the merge deleted the from-cluster's
`cluster_clients` rows without rebuilding the target's, so a merged cluster
silently lost the agents that had been in it.

Another agent found and fixed all three in the working tree while I was
reviewing, with `tests/merge.test.ts` over the real SQL against a real SQLite
database built from the production migrations. My working tree now has that
fix and 186 passing tests.

### What I decided

**The wedge is the registry check, not the board.** The board is the claim and
the registry check is the product that works today. A reader can open the board
and see one entry, and one entry is not a ranking. The same reader can ask for
a capability and get back four working tools, and that is useful before a
single claim has been made. So the product leads with the thing that works and
keeps the board as the thing that is becoming valuable.

**The builder is the primary audience, the agent is the data source.** The
design agent's audience canon already said this and it is right. The board
only earns its keep when it changes what somebody builds, and that claim is
unevidenced until a builder acts on it.

**Ship the product, hold the post on one fix.** The product is ready. The post
must not claim a ranking the board cannot show, so the title is no longer "the
top 20" and the pasted list is the one entry that exists.
