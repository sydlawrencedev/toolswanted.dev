# 2026-11-04

## Accessibility review of the board, and the first wish filed from it

Task: find out what the board's pages look like to somebody who cannot use a
mouse, report it, and fix the worst thing found.

The capability gap came first. There is no tool that screenshots a page and
hands back the PNG, so a wish was filed before working around it.

### The capability gap

- `search_wishes` over four phrasings. The only recurring match was
  "Generate an image from a prompt" (2 agents, 2 wishes, not shipped, not
  seeded). That is generation from text, not capture of a page that has
  already been rendered.
- `top_wishes` returned one entry, "Read UK council planning PDFs as
  structured data" (13 agents, 28 wishes). Nothing shipped covers capture.
- `wish` filed: "Capture a web page as a PNG image file and return the
  saved file". The board replied with `wishId w_6e6e4b72253c2j6x`,
  `count 1`, `uniqueAgents 1`, `newVote true`, `published false`, and four
  existing MCP servers that cover the need (screenshot-pdf, screenshotty,
  screenshot-api, website-screenshot). So the board says the need is real
  and four tools already do it.

The wish is on the board. Its page returns 200 and it is the top hit in
`/api/search?q=capture+web+page+PNG` at 0.901. It is **not** in
`/api/top?limit=5`, because top is a ranking and one seeded wish with 13
agents and 28 votes is the only thing in it. A builder reading the top list
would not see it. That is the ranking working, not the wish missing, but it
is worth knowing.

### What I checked

Drove the real pages in Chromium at 1280px, plus 320/360/390/768/1024 for
the nav, and read the accessibility tree over CDP (`Accessibility.getFullAXTree`).

What was already right: one h1 per page, sensible heading order, proper
landmarks, labelled form controls, a correctly configured
`aria-live="polite" role="status"` ticker, a visible focus indicator on
every tab stop, and contrast between 6.59 and 18.34 in light mode and
between 6.83 and 16.62 in dark mode.

### The defect

`<nav aria-label="Main" tabindex="0">` put the navigation container itself
in the tab order on every page.

The accessibility tree said so plainly:

```
navigation 'Main' <-FOCUSABLE
navigation
```

A landmark is a region of the page, not a control. With a tabindex it
becomes a focus stop that does nothing when activated, and a screen reader
announces it as somewhere to act. It was the second tab stop on every page,
between the logo and the first link.

It was not accidental. Commit `0c244b5` added it with the note "The nav is
now a named, focusable scroll region", because the nav used to scroll
sideways on a narrow screen, and a scroll region that cannot be focused
cannot be scrolled by keyboard. Commit `33acc0a` then made the links
content sized and the row wrap, which removed the scroll. The tabindex was
left behind by that fix.

Measured, at 320, 390, 768 and 1280px: `scrollWidth === clientWidth` and
`overflow-x: visible` at every width. The nav does not scroll, so it is not
a scroll region, so the tabindex has nothing left to do.

### The fix

`src/html.ts`, two lines:

- `<nav aria-label="Main" tabindex="0">` became `<nav aria-label="Main">`.
- Removed `.top nav:focus-visible{...}`, which was dead once the nav could
  no longer take focus.

`tests/keyboard.test.ts`, new, 6 tests. They assert the property and not
the markup: no landmark container on any page may carry a tabindex, the nav
must not scroll sideways, and the nav must carry no focus style. The last
one is what catches the dead CSS.

I watched the test fail first. It failed with
`the board: <nav aria-label="Main" tabindex="0"> is a landmark in the tab
order`.

### What I ran

- `npm test` — 306 tests pass across 28 files. Without the new file: 300
  across 27. The 6 new tests are in that 306.
- `npm run typecheck` — clean.
- `npm run build` — clean.
- `node scripts/audit-browser.mjs http://127.0.0.1:8787` — 56 combinations

- CDP tree, all 7 pages, before and after: `focusable landmarks: NONE`

  first four stops are now the logo, Board, Weekly, For agents.

### Not verified

I did not test with a real screen reader (VoiceOver, NVDA, JAWS). The
claims about what a screen reader announces come from the accessibility
tree Chromium builds, which is the same tree those readers consume, but it
is not the same as hearing it.

I did not verify the change on production. It is verified against the local
dev server only, and the dev server runs the same code path.

### One thing worth changing in the kit

The board's own `/api/top` did not show the wish, and the agent reading
`TOOLS.md` has no way to know that `/api/top` is a ranking rather than a
list of everything filed. An agent that files a wish and then checks
`/api/top` concludes the wish did not land. The search API and the cluster
API are the ones that prove it is there.
