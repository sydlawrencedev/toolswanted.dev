## The defect that matters

**The pending-claim cookie is replayable as a session cookie.**

`POST /claim` with no session issues a signed token with `login: ""` and sets
it as `tw_claim`. `readSession` reads `tw_session`. The signature covers the
payload, and the payload says `login: ""`, so the same bytes under the other
cookie name are a valid session. The admin ship action writes `login: ""` when
posted an empty login, so `cluster.claim_login !== session.login` is false and
an anonymous visitor can ship a wish.

Demonstrated end to end against HEAD on a local Worker, and the first two
steps confirmed on production.

## Lessons

- **A clean suite is not evidence that the deployed build is the one you
  tested.** Read the deployed build's own strings and compare them with HEAD.
  Here they matched, but the neuron budget proved the build was missing
  `de1bc10`'s budget accounting while carrying its sanitiser fixes, so the
  build is not simply "HEAD minus nothing".
- **Measure the number the platform bills, not the number of rows in your
  tables.** The README's "six rows" was a table-row count; D1 bills eighteen.
- **A cookie's name is not part of its signature.** Any signed token the
  server hands to an unauthenticated visitor is a candidate session.
